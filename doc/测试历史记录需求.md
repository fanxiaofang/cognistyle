
# 需求文档

## 引言

本需求文档定义了 CogniStyle 认知风格测评系统中双人测试历史记录的持久化存储功能。当前系统完全依赖浏览器的 localStorage 存储历史记录，存在数据不稳定、易丢失等问题。本功能将引入基于 EdgeOne Pages Functions 与 KV 存储的持久化方案，确保用户的测试历史记录可靠保存，同时遵循现有架构规范及隐私保护原则。

## 术语表

- **History_Service**：前端历史记录服务层，负责与历史记录 API 交互
- **History_API**：部署于 EdgeOne Pages Functions 的后端端点，处理历史记录的增删改查
- **KV_Store**：EdgeOne Pages 提供的键值存储服务，用于持久化数据
- **History_Entry**：单条双人测试历史记录，包含目标用户信息、互补度分数、生成时间等
- **friendId**：用户完成测评后获得的公开标识符，同时作为历史记录集合的索引键（简化认证策略）
- **Dual_Report**：双人认知互补度报告
- **Local_Storage**：浏览器本地存储，用于临时缓存及快速访问
- **Snapshot**：用户单次测评结果的完整快照

## 需求

### 需求 1：历史记录持久化存储

**用户故事**：作为用户，我希望我的双人测试历史记录能够持久化保存，这样即使清除浏览器缓存或更换设备，历史记录也不会丢失。

#### 验收标准

1. 当用户生成双人互补报告时，History_API 应将该历史记录条目保存至 KV_Store
2. History_API 应使用 friendId 作为历史记录集合的索引键
3. KV_Store 应保留历史记录至少 90 天（与 Snapshot TTL 一致）
4. 当用户的 friendId 过期时，KV_Store 应通过 TTL 机制自动清理关联的历史记录
5. History_API 应对每个 friendId 的历史记录数量限制为最多 50 条

### 需求 2：历史记录读取与同步

**用户故事**：作为用户，我希望能够从服务器读取我的历史记录，并与本地缓存保持同步，从而在不同设备间访问相同的历史记录。

#### 验收标准

1. 当用户打开历史记录页面时，History_Service 应从 History_API 获取服务器端历史记录
2. 当服务器返回历史记录时，History_Service 应将其缓存到 Local_Storage 以提升后续访问速度
3. 当本地缓存存在且未过期（小于 5 分钟）时，History_Service 应优先使用本地缓存
4. 当本地缓存过期或不存在时，History_Service 应从服务器重新获取
5. 当用户生成新的 Dual_Report 时，History_Service 应同时更新服务器和本地缓存

### 需求 3：历史记录写入与更新

**用户故事**：作为用户，当我生成双人互补报告时，我希望系统自动记录此次测试，以便在历史记录中查看所有测试过的对象。

#### 验收标准

1. 当用户成功生成 Dual_Report 时，History_Service 应调用 History_API 添加历史记录条目
2. 当同一 targetFriendId 已存在历史记录时，History_API 应更新该条目而非创建新条目（更新时将完全覆盖原条目所有字段，包括 generatedAt）
3. History_Entry 应包含 targetFriendId、targetProfileId、targetDisplayName、targetCallSign、targetDepartment、overallScore、pattern、generatedAt 字段
4. 当历史记录数量超过 50 条时，History_API 应删除最旧的记录
5. 当写入失败时，History_Service 应降级到仅更新 Local_Storage，并向用户显示警告

### 需求 4：历史记录删除

**用户故事**：作为用户，我希望能够删除单条或全部历史记录，以便管理我的隐私和数据。

#### 验收标准

1. 当用户点击删除单条历史记录时，History_Service 应调用 History_API 删除指定的 targetFriendId 条目
2. 当用户点击清空全部历史记录时，History_Service 应调用 History_API 删除该 friendId 下的所有历史记录
3. 当删除操作成功时，History_Service 应同时清除 Local_Storage 中的对应缓存
4. 当删除操作失败时，History_Service 应仅更新 Local_Storage，并向用户显示警告
5. History_API 应验证 friendId 有效且存在（friendId 作为隐式认证令牌）

### 需求 5：隐私与安全

**用户故事**：作为用户，我希望我的历史记录是私密的，只有我自己能够访问和修改。

#### 验收标准

1. History_API 应验证 friendId 有效且存在（friendId 作为隐式认证令牌）
2. History_API 应验证 friendId 格式符合规范（6-32 个字符，仅允许字母、数字、下划线、连字符）
3. History_API 应对每个 IP 地址实施速率限制：60 秒内读取请求不超过 30 次，写入请求不超过 10 次，删除请求不超过 5 次
4. History_API 不得在历史记录中存储敏感信息（如 deleteToken、原始作答数据）
5. 当 friendId 不存在或已过期，且请求为 POST/DELETE 时，History_API 应返回 404 错误
6. 当 friendId 不存在或已过期，且请求为 GET 时，History_API 应返回 200 OK 及空数组（对新用户友好）

### 需求 6：API 端点设计

**用户故事**：作为开发者，我需要清晰定义的 API 端点来实现历史记录功能，以便前后端正确集成。

#### 验收标准

1. History_API 应提供 `POST /api/dual-history` 端点用于添加或更新历史记录
2. History_API 应提供 `GET /api/dual-history/:friendId` 端点用于读取历史记录
3. History_API 应提供 `DELETE /api/dual-history` 端点用于删除单条或全部历史记录
4. History_API 应返回标准化的 JSON 响应格式（成功响应为 `{ data: { ... } }`，错误响应为 `{ error: { code: "...", message: "..." } }`）
5. History_API 应使用 COMMON_HEADERS 设置 CORS 及安全响应头

### 需求 7：错误处理与降级

**用户故事**：作为用户，当服务器不可用时，我希望系统能够降级到本地存储，以便我仍然可以查看和管理历史记录。

#### 验收标准

1. 当 History_API 请求失败（网络错误、超时、5xx 错误）时，History_Service 应降级到使用 Local_Storage
2. 当降级模式激活时，History_Service 应在界面上显示“离线模式”提示
3. 当服务器恢复可用时，History_Service 应自动同步本地修改到服务器（通过监听网络状态变化及定期健康检查）
4. History_Service 应在本地记录待同步的操作队列（添加、删除），当队列长度超过 20 条操作时，应采用 FIFO 策略丢弃最旧操作；队列中超过 7 天未成功同步的操作将被自动清理
5. 当同步冲突发生时（服务器版本比本地缓存更新），应优先使用服务器版本覆盖本地

### 需求 8：向后兼容与迁移

**用户故事**：作为现有用户，我希望我在 localStorage 中的历史记录能够自动迁移到新的持久化系统，从而不会丢失已有数据。

#### 验收标准

1. 当用户首次使用新版本时，History_Service 应检测 Local_Storage 中的旧版历史记录
2. 当旧版历史记录存在且用户持有有效的 friendId 时，History_Service 应将旧记录批量上传到服务器（使用批量端点或分批、延迟机制，确保不触发速率限制）
3. 当迁移成功时，History_Service 应在 Local_Storage 中标记迁移完成状态
4. 当迁移失败时，History_Service 应保留旧版数据并在下次启动时重试
5. History_Service 应在迁移过程中向用户展示进度提示

### 需求 9：性能优化

**用户故事**：作为用户，我希望历史记录功能响应迅速，不影响整体应用性能。

#### 验收标准

1. History_Service 应在后台异步执行历史记录写入操作
2. History_Service 应使用防抖机制避免短时间内重复请求（500ms 防抖）
3. History_API 的读取请求应在 200ms 内完成响应（P95）
4. History_Service 应限制单次读取的历史记录数量为最多 50 条
5. History_Service 应使用 stale-while-revalidate 策略（立即显示缓存数据，同时后台更新）

### 需求 10：数据结构与版本控制

**用户故事**：作为开发者，我需要明确的数据结构定义和版本控制机制，以便安全地演进历史记录功能。

#### 验收标准

1. History_API 应在请求/响应的顶层包含 version 字段标识协议版本（初始值为 `"history-v1"`）
2. History_API 应验证请求中的 version 字段与当前支持的版本是否匹配
3. 当版本不匹配时，History_API 应返回 409 CONFLICT 错误并提示升级
4. History_Entry 应使用与 Dual_Report 相同的类型定义（ProfileId、CompatibilityPairPattern）
5. History_API 应在 KV_Store 中使用 `"history:{friendId}"` 作为键前缀
