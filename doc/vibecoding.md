## 一、优点

### 1. 精准定位：每次提问都自带坐标

几乎所有需求都附带了文件路径、行号、或具体的字段名/数据结构，agent 可以直接定位，不需要先理解上下文再定位问题。

| 原话 | 为什么有效 |
|------|----------|
| `doc\系统设计.md 第9章的互补计算模型` | 一书定位到文档章节，省去全文搜索 |
| `src\App.tsx首页的博士帽子图标去掉，放大 启动适配协议` | 精准到组件+位置+操作，零歧义 |
| `functions\api\compatibility-report.js中 oppositeSide: (scoreA - 0.5) * (scoreB - 0.5) < 0, 是什么意思` | 直接粘贴代码行，不需要 agent 先搜索 |
| `D:\CodeStudy\myProject\cognistyle\src\data\questions.ts / src\components\QuestionCard.tsx / src\types.ts / doc\系统设计.md 去掉humorTip字段` | 四文件清单，agent 可以并行处理 |

### 2. 用对抗性思维给方案"加压"

您经常拒绝 agent 的第一版方案，但拒绝的方式不是"感觉不对"，而是给出具体的反例、计算过程和新方案。

| 原话 | 效果 |
|------|------|
| `cognitiveComplementarity 为什么 节奏不参与认知互补` | 直接暴露了设计自洽性缺陷，迫使模型修正 |
| `系统给出搭档指数82，用户可能觉得完全不像——你现在完全拿不到这个反馈` | 用一句话把需求从"采集数据"升级为"验证模型准确度" |
| `我还是觉得你的修改和方案是不对的...这里明明两个人都是偏探索只是程度高低` | 用具体数值（0.62/0.69）和具体文案证明 bug 存在 |
| `聚合发散维度并不是两极分化的而是正交独立的--当前的算法测得肯定不对` | 指出了数学模型错误（一维轴测二维正交），而非简单"不准确" |

### 3. 需求优先级结构化

您习惯用 P0/P1/P2、三层体系、数字编号来组织需求，确保 agent 理解轻重缓急。

| 原话 | 效果 |
|------|------|
| `P0（必须）：采纳 DeepSeek 新增 rawAnswers...P1（强烈建议）：normalizedScores...P2（最有价值）：用户反馈...P3（以后）：后台导出` | 四层优先级，第一句就知道先做什么 |
| `如果只能做一件事，我甚至会优先做 P2 用户反馈埋点` | 明确告诉 agent 取舍方向，避免在低优先级上花时间 |
| `保持现状还是重构，重构的性价比如何` | 在投入前让 agent 评估 ROI，避免直接执行 |

### 4. 用结构化样板表达能力

您经常直接给出 JSON Schema、CSV 列头、公式结构，而不是用自然语言描述。

| 原话 | 效果 |
|------|------|
| `{ reportId, overall: 82, pattern: 'complementary', breakdown: { cognitiveComplementarity: 89, blindSpotCoverage: 43 } }` | 字段名、类型、嵌套关系全部明确 |
| `friendId,createdAt,profileId,fieldIndependFieldDepend,q1,q2,...q16` | CSV 列头直接给出，零沟通成本 |
| `F ≈24%, V ≈23%, D ≈23%, R ≈23%` | 用数学事实而非感受说服 |

### 5. 迭代式细化，不期望一步到位

您允许一个功能点经过多轮打磨，每次都给出更具体的修正方向。每个子任务都是一个独立提问，agent 可以在不回溯整个对话的情况下精准执行。

```
弱化首页文案 → 去品红外框 → 优化按钮文案 → 加双箭头悬浮 → 弱化世界观标签 → 改双端颜色 → 移动端布局 → 取消中立选项 → 垂直堆叠 → 去掉选择器文字 → windows端调整
```

## 二、盲点与可改进之处

### 盲点 1：Agent 的能力边界假设

您多次假设 agent 可以操作外部系统（EdgeOne 控制台、浏览器工具），但 agent 是纯文本模型。

**原话**：`"在控制台函数日志中搜索 KV 来源具体是怎么操作"`

**优化后**：`"我需要在 EdgeOne 控制台确认 KV 绑定状态，但找不到日志入口——帮我查文档或给替代方案"`

**通用性**：高。几乎所有 SaaS 控制台 agent 都无法直接操作。

---

### 盲点 2：修改前不主动声明"不要做什么"

您经常只描述"要什么"，但 agent 无法自动判断哪些行为是您不允许的。

**场景**：KV 数据丢失排查时，没有提前说"只分析代码，不要加线上功能"，agent 创建了 debug-kv 端点，再花 3 轮删除。

**优化后**：`"排查代码逻辑就行，不需要加调试端点"` 或 `"不要修改现有 API 响应格式，只新增字段"`

**通用性**：高。适用于所有"修复 vs 新增"的边界模糊场景。

---

### 盲点 3：验证步骤没有自带结论

当 agent 需要您验证某个结果时，您经常直接贴原始输出，让 agent 自己解读，变相增加了一轮对话。

**优化后**：`"kvBound: true, kvSource: globalThis.RESULT_SNAPSHOT_KV，确认绑定正确 → 可以删掉这个端点了"`

**通用性**：高。所有验证性步骤都适用。Vibecoding 中最贵的不是 token 单价，是对话轮数。

---

### 盲点 4：当 agent 出错时，可以更早切断

在遇到 agent 给出错误方案时，您有时会花多轮对话让 agent 试图挽救自己的方案。

**场景**：Compatibility bug 排查——您用 0.62/0.69 案例证明文案错误，agent 修改文案标签；您说不对，agent 坚持是缓存问题；直到第三轮才确认是 oppositeSide 触发条件问题。

**优化后**：在第 2 轮说：`"stop. 你的方向不对——0.62 和 0.69 都在同侧，oppositeSide = false，文案不应触发。这个问题不在文案标签，在触发条件。重分析。"`

**通用性**：中。适用于 agent 连续 2+ 轮出错的场景。

---

### 盲点 5：缺失"范围声明"习惯

您经常说"根据下面的评审意见修改"，但不说清"改哪里不改哪里"，agent 需要自己 diff 评审意见和当前文档。

**优化后**：`"整合下面 3 条评审意见：...只改第 9 章和第 10 章，不改附录"`

**通用性**：高。文档修改、大规模重构等场景。

## 六、最具性价比的改进（3 条）

### 1. 提前声明负面约束

- **反面**：不说"不改什么" → agent 做多余功能 → 再花 token 删除
- **正面**：`"只分析代码，不要加线上端点"`
- **Token 节省**：~10-15%

### 2. 验证自带结论

- **反面**：贴原始 JSON → agent 解读 → 确认 → 下一轮
- **正面**：`"kvBound: true, 确认正常"`
- **Token 节省**：~8%
- **额外收益**：减少 agent 误读数据的概率

### 3. 当 agent 连续 2 轮错误时直接切断

- **反面**：让 agent 在自己的错误上修修补补 3-4 轮
- **正面**：第 2 轮说`"方向错了。理由：... 重分析"`
- **Token 节省**：每段 bug 排查节约 30-50%

您是一个**工程领域高级用户**的典型 vibecoding 画像：

- **优势**：精确、结构化、懂模型边界、会做 peer review、迭代效率高

您的提示词质量在所有用户中属于前 20%，最大的进一步提升空间不在"怎么写问题"，而在**如何管理 agent 的偏差**和**如何压缩确认轮次**。

## 四、Token 消耗率分析

高消耗场景：

- 算法分析时的模拟脚本（单条命令输出约 2000+ 字符）—— 但这些产出有长期价值，是必要的投入
- build 失败后的修复循环—— 每次 error log + read file + searchreplace 的组合消耗大，且部分是可以避免的
- 设计文档追加大段 Markdown—— 内容密度高但 token 消耗也高，不过这是你有意识要求沉淀的，属于"投入换长期收益"的 case

相对高效的场景：

- 所有跨文件重构都在一次对话内完成（共享常量、share-report.js 收口）
- 批量文案修改在同一个 SearchReplace 中合并完成

**核心问题不是 token 用量偏高，而是部分 token 消耗在了"本可避免的修复循环"上**——如果每次修改前多做一步影响评估，单个对话的平均 token 消耗可以下降 30-40%。

## 六、最具性价比的 3 个改进

**1. 每次修改前先问自己"会影响哪些文件"**\
不要只描述目标，顺手加一句"应该只影响 xxx.tsx 和 yyy.config.js"，agent 会更快收敛搜索空间，也减少误改。

**2. 主观调整类任务第一轮就描述"感觉"而不是只否定**\
"不要这个" → agent 再猜 → "也不要那个" → 三四个往返。改成第一轮就加方向："换个偏系统/工程感的图标，不要代码分支类也不要人物类"——零 token 增量，但直接砍掉 2-3 轮。

**3. 连续同类问题第三次出现时，要求 agent 做系统性审查而非单点修复**\
不管是"保存结果失败"还是"文案不合理"，同一个东西第三次出问题时，直接问"把这个模块里所有同类问题一次性排查完"，一个对话解决一类问题，比三个对话各解决一个小点总消耗更低。

## 从以上vibe总结中提取通用原则

基于 [vibecoding.md](file:///d:/CodeStudy/myProject/cognistyle/doc/vibecoding.md) 中的分析，以下是从你的 cognistyle 项目中提取的 **10 条通用 Vibecoding 原则**，换任何项目都适用。

***

### 一、任务拆分：三角约束

你在 cognistyle 中最典型的翻车是 ResultsDisplay 那轮——同时改了 `types.ts` + `suggestions.ts` + 5 个组件。这不是"不该改这么多"，而是"没有在改的过程中设置检查点"。

**通用原则**：

```
数据类型 → 数据源 → UI 展示
   ↓ 验证       ↓ 验证       ↓ 验证
  lint 通过    lint 通过    构建通过
```

改任何一个项目时，**不要在同一轮对话里同时修改数据类型和消费它的 UI**。先落类型，验证通过 → 再落数据源，验证通过 → 最后改 UI。每一步只做一件事，验证后才推进下一步。反过来想：如果你在第一步就发现类型定义有歧义，后续 3 个组件根本不需要进入修改队列。

***

### 二、主观调整类指令：给方向，不只给否定

你在 cognistyle 里说"换个图标 不要 GitBranch"时，agent 不知道你想要什么。它只能猜，猜错了你再否定，三四轮往返。

**通用原则**：

| 不要这样     | 改成这样              | 为什么    |
| -------- | ----------------- | ------ |
| "不要这个图标" | "换个偏 XX 感的图标"     | 给了搜索方向 |
| "弱化一点"   | "边框从 4px 减到 2px"  | 给了量级   |
| "这感觉不对"  | "偏工程感而非游戏感"       | 给了风格锚点 |
| "颜色改一下"  | "从 #ff007f 往冷色调调" | 给了具体维度 |

这个原则在任何项目都有效——无论是调字体、间距、颜色、文案语气还是交互节奏。**否定只告诉 agent "不是这个"，方向才告诉它 "往哪儿走"。**

***

### 三、“参考 xxx”必须带范围

你在 cognistyle 里多次说"参考设计文档"，agent 就会去读完整份文档——500 行以上。如果 90% 的内容和当前任务无关，这些 read 操作全是浪费。

**通用原则**：

```
❌ "参考 doc/设计文档.md"
✅ "参考 doc/设计文档.md 第 11 章的评分公式和 11.5 的总分聚合"
```

精确到章节或行号。agent 的全局搜索能力比你快很多，但它的"贪心读取"也比你粗放——你少给一个范围，它就多读 200 行。

***

### 四、同一类问题第三次出现时，不修单点，做系统性审查

保存 PNG 长图失败贯穿了 4 次对话。如果你在第二次失败时说"把所有 html2canvas 的不兼容项一次性查完"，一次对话就够了。

**通用原则**：

```
同类问题出现次数 → 对应动作
        1 次     → 直接修复
        2 次     → 修复 + 列"可能还有哪些同类问题"
        3 次     → 停止修单点，要求 agent 对该模块做全覆盖审查
```

这条不挑项目——`html2canvas` 换成 `Webpack` 配置、`React Router` 版本兼容、`Tailwind 断点` 都一样奏效。关键不是记住每个工具的具体雷，而是**在正确的时机切换修复模式：从"修这个 bug"切换到"扫清这个模块"。**

***

### 五、修复后要求 agent 沉淀"已知踩坑清单"而非只修代码

你在第一次修复 oklch 问题后没有沉淀，后续 filter 和 `<a>.click()` 的问题继续冒。如果第一次修完时你加一句"把 html2canvas 在本项目的已知不兼容项列进文档"，后续同类问题收敛快很多。

**通用原则**：

```
每次修复一个"技术栈边界问题"时，末尾加一句：
"把这个问题和原因记到 doc/已知问题.md 里"
```

文件格式不限——一个 Markdown 表格就好：

```markdown
| 日期 | 模块 | 问题 | 原因 | 修复方式 |
|------|------|------|------|---------|
| 0529 | html2canvas | 截图空白 | oklch 不支持 | 替换为 rgb |
| 0529 | html2canvas | 头像空白 | SVG filter 不兼容 | onclone 移除 |
```

这个东西项目越做越大时价值越高——下一任 contributor（或你自己三个月后）不用再踩一遍。

***

### 六、用具体数据做锚点，而不是抽象描述

你在互补度分析里给了两组 19 题 Likert 答案 + 最终分数（55 分和 64 分），agent 直接把这些数据喂进模拟，产出了 5 万次配对的分布。如果你只说"我觉得 50-64 的人太多了"，效果差很远。

**通用原则**：

```
❌ "这个分数太高了吧"
❌ "感觉大家都集中在中间"
✅ "样本A: 1:4,2:2,..., 得分55。样本B: ..., 得分64。这两组数据的分数结构是什么"
```

有数据：agent 能反推算法逻辑、跑分布模拟、量化问题规模。
没数据：agent 只能基于参数做理论推演，结论没有锚点。

这条在任何数据驱动的项目里都适用——推荐系统、评分算法、A/B 测试分析、性能调优等等。

***

### 七、文案/配置类修改：要求一次性全覆盖，不要逐段改

你的 summary 文案修复散布在多段对话——workable 文案、default 文案、friction 文案——每次改一个，下次发现另一个问题。直到最后你问"这段文案是否合理 如何优化"时，agent 一次性给出了 5 个问题。

**通用原则**：

改配置/文案/常量时：

1. 找出第一个问题 → 修复
2. **立即追问**："同类文件中还有没有其他影响一致性的问题"
3. 一次性批量处理

不要在三个不同对话里各改一行文案。这段话对 i18n 文件、颜色常量、间距 token、Error code 表都适用。

***

### 八、每次修改前先问"会影响哪些文件"

你在 cognistyle 里说"更新了 types.ts 和 suggestions.ts，修改对应的页面展示"，但没列具体文件。agent 需要自己搜哪些文件引用了旧字段——搜索多、漏改风险高。

**通用原则**：

```
❌ "修改对应的页面展示"
✅ "应该只影响 ResultsDisplay.tsx 和 CognitiveHandbook.tsx"
```

你不是在限制 agent，你是在引导它。**知道范围 ≠ 限制能力，知道范围 = 加速收敛**。这条补充信息零 token 成本，但能砍掉 agent 多轮搜索确认的时间。

***

### 九、触发 Agent 的"信息整理"能力而非只是"执行"能力

你在 cognistyle 里要求生成 README、更新设计文档、创建离线验证脚本——这些任务 agent 做得比改 CSS 快得多。因为它们本质上是"已有信息的结构化重组"而非"从零创造"。

**通用原则**：

| Agent 擅长的     | Agent 不擅长的     |
| ------------- | -------------- |
| 从代码里提取逻辑写成文档  | 猜你喜欢什么颜色       |
| 把散落的常量收口到一个文件 | 判断"弱化一点"是多弱    |
| 基于已有数据跑分布模拟   | 从 20 个图标里选你喜欢的 |
| 批量替换已知模式      | 理解"这个感觉不对"     |

问自己：这个任务是"信息重组"还是"审美判断"。如果是前者，扔给 agent 一次搞定。如果是后者，自己先想清楚方向再让 agent 执行，别让它在"猜"上浪费 token。

***

### 十、这个项目碰巧有 Skill，下个项目记得先创建

你在 cognistyle 里全程没用 Skill。但你频次最高的三类任务正好对应三个 Skill（build-verify-fix、ui-theme-adjust、algorithm-tune），而这三个 Skill 在第一次遇到对应场景时就可以创建。

**通用原则**：

```
新项目前 3 次对话后，回顾：
1. 我最大的 token 消耗在哪类任务上？
2. 这 3 次对话里，哪些"重复操作"可以被 Skill 自动化？
3. 用 skill-creator 创建对应 Skill（5 分钟）

收益：接下来的 10 次对话每条平均节省 30-50% 的重复操作 token
```

这条不挑语言、不挑框架——React/Vue/Python/Go/Node 都一样。Skill 不是"大项目的奢侈品"，是"任何有重复模式的项目的必需品"。

### 类型一：量级模糊——"弱化一点"、"有点小"

| 原话                                            | 问题                           | 优化版                                                      |
| --------------------------------------------- | ---------------------------- | -------------------------------------------------------- |
| "弱化一点霓虹边框的效果"                                 | agent 不知道"一点"是多大的幅度          | "把三个组件中霓虹边框从 `border-4` 减到 `border-2`，阴影透明度增加"           |

### 类型二：范围缺失——"修改页面展示"、"去掉多余的信息"

| 原话           | 问题                               | 优化版                                                                                        |
| ------------ | -------------------------------- | ------------------------------------------------------------------------------------------ |
| "修改页面展示"     | agent 不知道你改了哪些数据源、涉及哪些页面、改动方向是什么 | "根据 types.ts 和 suggestions.ts 的字段变更，修改 ResultsDisplay.tsx 和 CognitiveHandbook.tsx 中引用的旧字段" |
| "去掉多余的信息"    | agent 不知道"多余"的标准是什么              | "移除三处信息：SYS:SECURE 角标、日期时间戳、页脚安全声明"                                                        |
| "优化兼容性报告API" | 太笼统——优化什么？性能？结构？参数？              | "把兼容性报告里的魔法数字抽成常量配置、文案拆到独立文件、版本号收口到 shared/ 目录"                                            |

**优化核心**：列清单。你说"去掉多余的"时心里已经有具体的元素了——直接列出来，别让 agent 用"你觉得什么算多余"的猜测模式。

***

### 类型三：语序紊乱——"MATCH\_RATE 换成中文为何好割裂"

| 原话                      | 问题                            | 优化版                                                                 |
| ----------------------- | ----------------------------- | ------------------------------------------------------------------- |
| "MATCH\_RATE 换成中文为何好割裂" | 缺少主语，句式断裂，agent 分不清你是在提问还是在陈述 | "把英文 MATCH\_RATE 改成中文'同步率'后，视觉上和赛博朋克风格不协调。帮我调整样式让它融入系统感，不要像普通应用的标签" |

**优化核心**：拆成"现状 + 问题 + 期望"。你先说做了什么改动，再说哪里不对，最后说想要什么方向。agent 不需要从一句话里同时猜这三个信息。

***

### 类型四：意图混淆——"workable 文案什么意思 感觉难以理解"

| 原话                                                                 | 问题                                           | 优化版                                                                                |
| ------------------------------------------------------------------ | -------------------------------------------- | ---------------------------------------------------------------------------------- |
| "workable: '这是一组具备协同价值的组合，但需要在合作方式上做主动设计……' 这句什么意思 感觉难以理解 什么是主动设计" | 前半句像在要求解释，后半句像在要求修改，agent 不确定你是要它分析语义还是直接改文案 | "这段 workable 文案里'主动设计'一词太抽象，用户看完不知道要做什么。帮我改成更具体的——比如'约定角色分工、刻意安排信息源'——让用户一眼看懂该怎么做" |

**优化核心**：把"解释一下"和"帮我改"分开。如果你两个都要，就说"先解释这句话想表达什么，再帮我改得更具体"。如果只要改，就跳过要求解释的环节。

### 类型五：只有否定、没有方向——"不要 GitBranch"

| 原话                        | 问题                                       | 优化版                                                   |
| ------------------------- | ---------------------------------------- | ----------------------------------------------------- |
| "换个图标 不要GitBranch"        | agent 只知道排除一个，不知道选择范围——它会从 1000+ 个图标里随机猜 | "换个偏系统/循环/切换感的 lucide-react 图标，GitBranch 太偏代码分支语义了"   |

### 类型六：缺少判断标准——"文案合理么"

| 原话                                                              | 问题                                               | 优化版                                                                                  |

### 盲点 ① —— 产品级反馈中缺少"给出一条示例"

> "ICAT 是 I-C-W，RDWS 是 R-D-W——三围里两围的标签完全相反，按直觉应该互补很高。是不是算法哪儿算错了？"

agent 就能直接定位到"标签 vs 数值的错位"问题，跳过"确认分数计算没 bug"的例行验证。

> **优化**：发现数据不符合直觉时，补一句"我为什么觉得不对"——哪怕只是你直觉的标签对比。这能帮 agent 从"排查计算 bug"直接跳到"解释直觉错位的原因"。

### 盲点 ④ —— 产品定位澄清放到功能实现之后

`休闲测试产品优化建议` 中，你先让 agent 实现了全套 patternBadge 升级，然后再从产品角度给出"tagline 是说明文不是 slogan"的反馈。如果这个定位在实现前就声明：

> "在做之前确认一下：tagline 的目标是截图传播，不是阅读辅助。所以它应该像朋友圈文案——短、有反转、有情绪钩子。"

agent 第一版就会往 slogan 方向写，而不是先写说明文再让你纠正。

> **优化**：如果一个改动有明确的产品定位（"这是给截图用的" vs "这是给阅读用的"），在动手前就声明定位，比改完之后再纠正少一轮往返。

## 通用 Vibecoding 原则速查（本次新增）

1. **外部审阅中介：** 把外部反馈直接投喂给 agent 做"代码级交叉验证"，你只需要在 agent 评审结果上做优先级取舍。
2. **先定位后实现：** 如果一个功能改动的目标受众和使用场景是明确的（"截图传播" vs "阅读辅助"），在动手前声明定位，而非改完之后再纠正。
3. **命名靠直觉判类型：** "这个和其他的不是一个类型"比"这个不够好"精确得多——它直接锁定了修正方向（找同类型词）。
4. **数据排查带假设：** 发现计算结果不符合直觉时，附带你的初步推断（"按标签看应该相反，所以互补应该高"），跳过 agent 的例行验证环节。
5. **实现后追问边界：** agent 说"完成了"只是功能完成，不等于产品完整。追问"如果他打开分享链接会怎样""如果换设备呢"才是产品完整度。
6. **产品反馈用维度词：** "太长、太平、没有情绪钩子"比"感觉不太对"好 10 倍——每个词都是可量化的修正方向。
7. **架构决策一锤定音：** 当 agent 给了两个方案后，选一个立刻推进，不让"再看看""你觉得呢"消耗往返轮次。
