|---|---|---|---|---|

### 三个维度解释

|维度|左极描述|右极描述|
|---|---|---|

|认知视角|优先把握整体结构、系统关系与长期影响|优先关注组成部分、关键细节与执行精度|
|问题路径|喜欢探索未知可能性，乐于尝试新的思路和方案|更关注目标达成，倾向寻找明确、稳定、可执行的路径|

## 4. 单人计分模型

推荐的五档文案
不要显示数字，显示语义：

◉ ○ ○ ○ ○   非常接近左侧
○ ◉ ○ ○ ○   略偏左侧
○ ○ ◉ ○ ○   两种方式都差不多
○ ○ ○ ◉ ○   略偏右侧
○ ○ ○ ○ ◉   非常接近右侧


既然题型已经从：

```text
单陈述 Likert
↓
非常不同意 ~ 非常同意
```

改成了：

```text
双端选择（Bipolar Scale）

A ←→ B

强A  弱A  中间  弱B  强B
```

那么原来的计分模型其实应该整体重写，而不是修补

### 4.1 双端五档量表（Bipolar Scale）

每题提供两个对立但均合理的认知倾向。

例如：

```text
先理解整体结构
○ ○ ● ○ ○
先研究关键细节
```

用户从五档中选择最符合自己的位置。

| 选项 | 含义       | 原始分值 |
| -- | -------- | ---- |
| 最左 | 强烈偏向左侧   | -2   |
| 左侧 | 略偏向左侧    | -1   |
| 中间 | 两种方式都差不多 | 0    |
| 右侧 | 略偏向右侧    | +1   |
| 最右 | 强烈偏向右侧   | +2   |

默认未作答：

```text
0（中间）
```

---

### 4.2 单题计分

每道题定义：

```ts
{
  dimension: "wholist_analytic",

  leftText: "先理解整体结构",

  rightText: "先研究关键细节"
}
```

用户选择后得到：

| 选择 | rawScore |
| -- | -------- |
| 最左 | -2       |
| 左  | -1       |
| 中  | 0        |
| 右  | +1       |
| 最右 | +2       |

---

### 4.3 维度聚合

对于某个维度：

```text
dimRawScore
=
Σ(rawScore)
```

例如：

```text
整体/分析

-2
-1
0
+1
+2
+1

=

```

#### 理论范围

假设该维度有 N 题：

```text
dimMinScore = N × (-2)

dimMaxScore = N × (+2)
```

例如：

```text
6题

min = -12
max = +12
```

### 4.4 百分比归一化

为了统一结果页展示，将原始分数映射到：

```text
0 ~ 100
```

计算公式：

```ts
percentage =
(
  dimRawScore - dimMinScore
)
/
(
  dimMaxScore - dimMinScore
)
× 100
```

等价于：

```ts
percentage =
(
  dimRawScore + 2 * N
)
/
(
  4 * N
)
× 100
```

---

#### 示例

6题维度：

```text
dimRawScore = -12
```

得到：

```text
0%
```

完全偏向左极。

---

```text
dimRawScore = 0
```

得到：

```text
50%
```

两种方式均衡。

---

```text
dimRawScore = +12
```

得到：

```text
100%
```

完全偏向右极。

---

### 4.5 极性判定

引入**平衡区**（45-55），避免微小差异导致标签切换：

```ts
computePolarity = (percentage, leftKey, rightKey) => {
  if (percentage <= 44) return leftKey;
  if (percentage >= 56) return rightKey;
  // 45~55 balanced zone — return the closer one
  return percentage >= 50 ? rightKey : leftKey;
};
```

#### 场独立 ↔ 场依赖

```ts
polarity = computePolarity(percentage, 'fieldIndepend', 'fieldDepend');
```

---

#### 整体 ↔ 分析

```ts
polarity = computePolarity(percentage, 'wholistic', 'analytic');
```

---

#### 探索 ↔ 定向

```ts
polarity = computePolarity(percentage, 'exploratory', 'directed');
```

注意：

由于题库设计中统一采用：

```text
左侧 = 探索
右侧 = 定向
```

所以保持一致即可。

---

#### 冲动 ↔ 反思

```ts
polarity = computePolarity(percentage, 'impulsive', 'reflective');
```

### 4.6 偏好强度

计算：

```ts
distance = Math.abs(percentage - 50)
```

| 距离      | 强度       |
| ------- | -------- |
| ≤ 10    | balanced |
| 10 ~ 25 | moderate |
| > 25    | strong   |

对应展示：

| strength | 展示   |
| -------- | ---- |
| balanced | 均衡   |
| moderate | 偏向   |
| strong   | 显著偏向 |

例如：

```text
场独立 74%
```

```text
distance = 24
```

结果：

```text
偏向场独立
```

认知模式（cognitivePattern）公式化推演： 确保每个维度的特质精准对应：

信息校准 (FI/FD)：FI 依靠独立判断不被干扰，FD 通过外部反馈捕捉线索。
目标策略 (D/E)：D 锁定核心目标高效执行，E 探索未知多路径推进。
信息组织 (W/A)：W 关注宏观与整体关系，A 拆解微观细节逐个击破。
运行模式 (I/R)：I 在行动中验证修正，R 在行动前充分推演追求闭环。

### 5.2 原型匹配算法（认知空间距离模型）

将用户三个核心维度的归一化得分映射到三维认知空间：

|维度|左极|右极|
|---|---|---|
|场独立/场依赖|FI=0|FD=100|
|整体/分析|W=0|A=100|
|探索/定向|E=0|D=100|

用户坐标：

```text
P(x,y,z)
```

八个认知原型分别对应认知立方体的八个顶点。

例如：

```text
FI-E-W = [0,0,0]
FD-D-A = [100,100,100]
```

采用欧氏距离计算用户与各原型的距离：

D=\sqrt{(x_t-x)^2+(y_t-y)^2+(z_t-z)^2}

最大距离：

D_{max}=\sqrt{100^2+100^2+100^2}\approx173.2

匹配度：

MatchScore=100-\frac{D}{173.2}\times100

匹配度范围：

```text
0 ~ 100%
```

数值越高表示越接近该原型。

### 5.4 职业身份映射（8 原型 × 2 风格 = 16 职业子类型）

8 个认知原型与 2 种风格标签交叉，形成 16 种职业子类型：

```text
8 认知原型 × 2 风格标签（冲动/反思） = 16 职业子类型
```

职业身份由两层构成：

| 层级 | 来源 | 说明 |
|------|------|------|
| 认知原型（8 种） | 3 核心维欧氏距离匹配 | 决定职业大类和行会归属 |
| 风格标签（2 种） | 冲动/反思维度判定 | 决定同一原型下的职业子类型 |

例如，开拓者（FI-E-W）原型下：

## 7. 双人互补报告：功能设计

### 7.1 功能范围

- 用户完成单人测评后，保存结果快照并获得可分享的 `friendId`
- 输入好友 `friendId` 后生成双人认知互补度报告
- 双人报告通过分享链接进入
- 用户可主动删除自己的结果快照
- 生成脱敏公开分享报告

**不在范围**：不引入账号体系、不支持根据真实好友关系自动查找、不修改题库内容、不修改单人测评分数计算逻辑、不做多人团队版。

### 7.2 核心流程

**单人测评 → 保存快照**：用户完成测评 → 前端构建快照 → `POST /api/results` → 返回 `{friendId, deleteToken, expiresAt}` → 前端保存到 localStorage

**输入识别码 → 生成双人报告**：用户输入 `targetFriendId` → 读取本地 `myFriendId` → `POST /api/compatibility-report` → 返回 `CompatibilityReport` → 跳转双人报告页

**链接进入**：打开 `/dual?friend=<targetFriendId>` → 若本地有 `myFriendId` 则直接加载；若无则引导完成测评保存后再返回

**删除结果**：`POST /api/results/delete`（需 `friendId + deleteToken`）→ 后端校验 `deleteToken` → 删除快照 → 前端清理本地缓存

**公开分享**：`POST /api/share-report`（需 `myFriendId + targetFriendId`）→ 返回脱敏公开报告 token → 前端展示 `/share/<token>`

### 7.3 设计原则

- 保持现有单人测评与单人结果计算逻辑**完全不变**。
- 双人报告是**独立的业务模块**，不复用 `ResultsDisplay` 中的"第二身份"逻辑。
- `friendId` 只用于分享和检索；删除操作必须使用仅本人持有的 `deleteToken`。
- 互补度不是"越相反越高分"，而是**认知互补、盲区覆盖、摩擦风险**三个层面的综合判断。

### 7.4 数据模型

## 9. 互补计算模型

> **版本**：v6.3（4 子分透明化 · complementary 12.6% · 50k 模拟验证通过）
> **产品定位**：社交测试产品，而非心理测量工具。优化目标是"朋友之间有趣的搭档关系"——高分意味着彼此能形成有默契的搭档组合，低分也不代表关系差，只是提示协作中需要对齐的节奏差异。
> **设计原则**：
> - 绝大多数组合落中高分（社交分享需要正反馈）
> - 低分组合＜5%（两个愿意一起测的朋友本身已有关系基础）
> - 同质不是缺陷，互补也不是更高级——用模式区分，不用分数区分
> - 4 子分全部对应 UI 展示项，无黑箱
> - 对外展示为 **"搭档指数"**，不与"关系好坏"挂钩

### 9.1 输入向量

从单人快照中提取以下 4 个维度（0~1 归一化分数）：

| 层级 | 简写 | 维度名 | 维度 ID | 0 极 | 1 极 |
|------|------|--------|---------|------|------|
| 核心 | F | 信息参照（场定位） | `fieldIndependFieldDepend` | 场独立 | 场依赖 |
| 核心 | V | 认知视角（视野） | `wholisticAnalytic` | 整体 | 分析 |
| 核心 | D | 问题路径（方向） | `exploratoryDirected` | 探索 | 定向 |
| 风格 | R | 决策风格（节奏） | `impulsiveReflective` | 冲动 | 反思 |

> **设计原则（v5.6 重构）**：R（节奏）是**冲突/顺滑因子**，不是认知因子。R 仅进入摩擦风险评估（frictionRisk）和节奏协同（rhythmSynergy）两个通道，**不参与认知互补度和盲区覆盖**。核心三维（F/V/D）主导认知互补与盲区覆盖。此隔离策略防止 R 在 4 个层级重复计入导致结构过载（旧版 R 实际影响约 2.5–3.0 倍放大）。

#### 基础算子

对每一维，给定双方归一化分数 `scoreA`、`scoreB`：

```text
delta        = abs(scoreA - scoreB)                    // 差异度
strengthA    = abs(scoreA - 0.5) × 2                   // A 的倾向强度
strengthB    = abs(scoreB - 0.5) × 2                   // B 的倾向强度
avgStrength  = (strengthA + strengthB) / 2             // 双方平均强度
oppositeSide = (scoreA - 0.5) × (scoreB - 0.5) < 0    // 是否跨中位线异侧
```

### 9.2 维度互补评分函数（高斯核）

高斯核评分函数应用于**核心三维（F/V/D）**。R 不参与认知互补评分，但 R 在 `rhythmSynergy` 通道仍使用独立的高斯核（参数见下表 `rhythm` 行）：

$$\text{dimScore} = \text{floor} + (100 - \text{floor}) \times \exp\left(-\frac{(\Delta - \text{idealGap})^2}{2 \times \text{tolerance}^2}\right)$$

其中：
- `idealGap`：该维度上最有利于互补/协同的差异值（峰值位置）
- `tolerance`：峰值两侧的容忍宽度（越大越平缓，越能接受偏离 idealGap 的组合）
- `floor`：评分保底值（避免极端偏离时完全归零）

#### 维度参数（理论初值，待模拟校准）

| 维度 key | 层级 | idealGap | tolerance | floor | 用途 | 设计思路 |
|----------|------|----------|-----------|-------|------|---------|
| `field` | 核心 | 0.45 | 0.24 | 15 | cognitiveComplementarity + blindSpotCoverage | 场独立者独立判断 × 场依赖者借力外部，中高差异时互补价值最大；过低则无差异可补，过高则沟通成本反噬 |
| `vision` | 核心 | 0.50 | 0.27 | 15 | cognitiveComplementarity + blindSpotCoverage | 整体视角与细节视角是经典互补维度——差异越大覆盖越全；理想峰值靠近 0.5 |
| `direction` | 核心 | 0.30 | 0.25 | 15 | cognitiveComplementarity + blindSpotCoverage | 探索（发现可能）× 定向（锁定路径）的张力区间；差异过大会直接产生路线冲突，故峰值偏中段 |
| `rhythm` | 风格 | 0.20 | 0.22 | 15 | rhythmSynergy 专用 | 风格标签的差异峰值偏近——轻度节奏差异有益（快慢搭配），过度极化则摩擦。仅用于节奏协同评分，不参与认知互补 |

> **⚠ 以上参数为理论初值，未经模拟校准。floor=15 基于社交产品定位——两个愿意一起测的朋友已达基础关系门槛。注意：floor 仅作用于认知互补和节奏协同的 dimScore；摩擦风险不设 floor（0 差异 = 0 摩擦，真实反映协作顺畅度）。**

### 9.3 五个子分

#### A. 核心认知互补度 `cognitiveComplementarity`

衡量双方在认知风格上的互补程度。**仅 3 个核心维度参与**（R 已移出，见 9.1 设计原则）：

```
cognitiveComplementarity = fieldScore × 0.33 + directionScore × 0.34 + visionScore × 0.33
```

| 维度 | 权重 | 理由 |
|------|------|------|
| `direction`（问题路径） | 0.34 | 决策路径决定协作效率上限——探索↔定向的分工是最高价值的认知互补 |
| `field`（信息参照） | 0.33 | 判断框架互补是高价值协作的基础——"独立判断 + 外部借力"是经典组合 |
| `vision`（认知视角） | 0.33 | 整体 vs 细节互补是认知协作的底层逻辑 |

> **权重设计原则**：三维近似等权。方向≈场定位≈视野，取消 v5.6 的 D>F>V 阶梯——因为三者在高斯核评分中各自的 idealGap 和 tolerance 差异已经天然赋予了不同的实际影响力。

#### B. 盲区覆盖度 `blindSpotCoverage`

衡量双方在多大程度上能覆盖彼此的认知盲区。仅 3 个核心维度参与（行动节奏不属于认知盲区）。

**v6.3 公式（power transform 0.35 拉伸）**：

```text
coveragePotential = oppositeSide ? delta : delta × 0.5   // 跨中位线异侧全额，同侧半额
strengthFactor    = 0.7 × max(strengthA,strengthB) + 0.3 × min(strengthA,strengthB)
coverageScore     = 100 × coveragePotential^0.35 × strengthFactor
```

公式语义：
- **coveragePotential**：同侧仍有半额覆盖（两人即使同侧，也有一定程度的视角互补）
- **power 0.35**：比 v6.2 的 0.5 更激进地拉伸尾部——`pow(0.1,0.35)=0.449` vs `pow(0.1,0.5)=0.316`，对低 Δ 侧提升约 42%。使 blindSpot avg 13.2→16.7，p90 23→27
- **strengthFactor 0.7/0.3**：强方主导（占 70% 权重），弱方仅作补充。一强一弱 ≈60~80，双强异侧 → 满分

取 3 个核心维度 coverageScore 的算术平均值。

> **演进说明**：v5.6 `oppositeSide × avgStrength × delta` 对同侧组合归零过于严格，导致 blindSpot avg 仅 6.8。v6.2 引入同侧 0.5 折 + power 0.5 + 强方主导，avg 提升至 13.2。v6.3 将 power 降至 0.35（进一步提高低 Δ 侧可见度），avg 升至 16.7，p90 从 23→27。

#### C. 执行摩擦风险 `frictionRisk`

衡量双方差异在协作中可能产生的冲突与内耗。4 个维度全部参与：

```text
riskScore = delta > dangerStart
  ? (delta − dangerStart) / (1 − dangerStart) × 100 × (0.5 + avgStrength × 0.5)
  : 0
```

| 维度 key | dangerStart | weight | 理由 |
|----------|-------------|--------|------|
| `field` | 0.25 | 0.35 | 判断参照差异过大导致"鸡同鸭讲"式沟通成本 |
| `direction` | 0.30 | 0.25 | 探索↔定向对立时任务推进方式冲突 |
| `vision` | 0.30 | 0.15 | 整体/细节摩擦较温和，更多是节奏问题 |
| `rhythm` | 0.20 | 0.25 | 决策节奏差异是最直观的协作摩擦源（一方觉得拖沓一方觉得冒进） |

> **v6.3 dangerStart 校准**：从 v6.2 的 0.40~0.60 统一降低至 0.20~0.30，此前阈值高于 delta p90=0.43 导致 frictionRisk 几乎无反应。降低后 frictionRisk avg 从 0.8→4.0，p90 从 3→10，且与 cogComp 保持独立（不共线）。

```
frictionRisk = Σ(riskScore_i × weight_i)    // i ∈ {field, direction, vision, rhythm}
```

> **设计说明**：风格标签（rhythm）在摩擦风险中权重 0.25，与方向持平——冲动/反思的节奏差异在真实协作中极易引发"你怎么还没想好"vs"你怎么先动手了"的对立。R 仅在 frictionRisk 和 rhythmSynergy 两个通道参与评分，认知互补度和盲区覆盖已完全移除 R（v5.6 R 隔离策略）。

#### D. 节奏协同度 `rhythmSynergy`（风格标签专项）

作为风格标签维度参与计算的专项子分，衡量双方决策节奏的匹配质量：

```text
rhythmSynergy = rhythmDimScore × 1.0
```

即直接取节奏维度的 dimScore（高斯核评分）。设计意图：
- delta 接近 idealGap（0.20）时——轻度节奏差异，得分高：冲动者推动执行 + 反思者把关质量
- delta 过大时——节奏严重对立，得分低：双方互相消耗
- delta 过小时——节奏完全一致，得分中等：虽无摩擦但也无节奏互补

#### 子分权重汇总

| 子分 | 参与维度 | 在总分中权重 | 说明 |
|------|---------|-------------|------|
| `cognitiveComplementarity` | F + V + D（3 核心） | 0.60 | 认知互补是**主驱动力**——唯一 std=11.5 的子分，决定总分的大盘分布 |
| `blindSpotCoverage` | F + V + D（3 核心） | 0.15 | 盲区覆盖——power transform 0.35 拉伸后贡献中等区分度 |
| `frictionRisk` | F + V + D + R（4 维） | 0.15（反转） | 摩擦风险抵消互补收益，校准后 avg 4.0 独立于 cogComp |
| `rhythmSynergy` | R（1 风格） | 0.10 | 节奏匹配为辅助维度 |

> **v6.3 权重变更**：从 6 子分（含隐藏 synergyBoost+alignmentScore）简化为 4 子分（全部对应 UI 展示项），权重重分配 cogComp:0.55→0.60, blind:0.05→0.15, rhy:0.05→0.10, fricInv:0.10→0.15。删除 synergyBoost(0.20) 和 alignmentScore(0.05)。

### 9.4 搭档指数（主分）

> 报告中对外展示为 **"搭档指数"**——一个综合了认知互补、盲区覆盖、摩擦风险、节奏协同的综合数值。不是"关系好坏分"，而是"作为搭档的协同度分"。

**v6.3 公式（4 子分透明化）**：

```
partnerIndex =
  cognitiveComplementarity × 0.60 +
  blindSpotCoverage      × 0.15 +
  rhythmSynergy          × 0.10 +
  (100 − frictionRisk)   × 0.15

// homogeneous 保底分（floor，不是加分）
if pattern === 'homogeneous':
    partnerIndex = max(partnerIndex, 72)
```

**权重设计说明（v6.3）**：

| 设计决策 | 理由 |
|---------|------|
| cognitiveComplementarity 权重 0.60 | 它是唯一 std=11.5 的子分，做主驱动力破解"均分堆积" |
| blindSpotCoverage 权重 0.15 | 从 0.05 提升至 0.15 使盲区覆盖有可感知的影响力（v6.2 用户无法感知） |
| frictionRisk 权重 0.15 | 反转刹车，但控制在第三位（"互补"优先于"代价"的叙事） |
| rhythmSynergy 权重 0.10 | R 为辅助认知维度，权重最小 |
| homogeneous floor=72 | 同质组合不靠加分，而靠最小值保障——公式算出的分 + floor 取 max，保证最低 72 |

> 以上百分比为结构权重。各维度的实际有效影响力取决于评分函数和样本分布，已在 `scripts/compatibility-tuning.ts` 50,000 次模拟中验证。v6.3 删除 synergyBoost(0.20) 和 alignmentScore(0.05)，4 子分全部对应 UI 展示项，消除黑箱。

分值 clamp 至 `[0, 100]`。

### 9.5 搭档关系模式

> 不做能力评级，不暗示某个模式比另一个"更好"。每个分数区间是一个**协同潜力标签**，描述的是"你们作为搭档的协同潜力"，而非"你们合不合得来"。

| 搭档指数 | （协同强度标签） | 代码标签 | 叙事方向 |
|----------|---------|---------|---------|
| 80 – 100 | 默契 | `harmonious` | 认知互补 + 节奏匹配 + 低摩擦，天生搭档说的大概就是你们这种 |
| 65 – 79 | 共振 | `synergistic` | 有较强互补价值，主要优势已经形成稳定协作 |
| 50 – 64 | 互补 | `complementary` | 部分维度互补，明确分工后会逐渐发现彼此的妙处 |
| 35 – 49 | 探索 | `exploratory` | 有局部补位空间，日常协作需要刻意对齐但值得尝试 |
| 0 – 34 | 挑战 | `dynamic` | 协作结构尚未稳定形成，容易碰撞但也有机会撞出新东西 |

`homogeneous` 模式固定标签为 🪞 **回声组**（不参与分数区间判定）。注意："回声组"不是低分——v6.2 通过 homogeneous floor=72 保证同质组合最低 72 分。

> **设计原则**：用户看到"化学反应组 38分"不会觉得"关系差"——化学反应本身就是一种有趣的搭档形态。所有标签均为中性或正面意象。

#### pattern → badge 映射层（v5.6 新增）

工程 taxonomy（4 patterns）与叙事 taxonomy（badge）之间的强绑定关系。防止长期维护中 pattern 与 badge 语义漂移（dual taxonomy 风险）：

| pattern（工程判定） | badge（叙事展示） | 绑定规则 |
|---------------------|-------------------|---------|
| `homogeneous` | 回声组 🪞 | 固定绑定——四维平均 delta < 0.15 即为同质 |
| `complementary` | 经纬组 🧩 | 固定绑定——盲区覆盖高 + 中度差异 |
| `asymmetric` | 双星共轨组 ⚙️ | 固定绑定——不满足同质/互补/冲突的兜底 |
| `conflicting` | 化学反应组 ⚡ | 固定绑定——高摩擦 + 极端差异 |

> 代码实现中 `pattern → badge` 为 1:1 映射，tagline/emoji/颜色均通过 badge 查询。pattern 仅用于工程判定，不直接暴露给前端展示层。


### 9.6 组合模式判定（v6.3 绝对阈值 + complementary 优先）

按优先级顺序评估，每对组合必定落在 4 个 pattern 之一。**pattern 判定仅使用 raw 值**（raw delta / raw coverage / raw friction），禁止使用 composite index（partnerIndex）：

| 顺序 | 模式 | 条件 | 所用值 |
|------|------|------|--------|
| 1 | `homogeneous` | 四维平均 delta < 0.12 | raw delta（4维平均） |
| 2 | `complementary` | `blindSpotCoverage ≥ 25` **且** `cognitiveComplementarity ≥ 70` | raw coverage / raw cogComp |
| 3 | `conflicting` | `frictionRisk` ≥ 30 **或** 两维及以上 delta > 0.50 | raw friction / raw delta |
| 4 | `asymmetric` | 兜底（不满足以上任一） | — |

**判定顺序说明**：complementary 优先于 conflicting——高互补 + 高摩擦的组合应判定为互补（化学反应组），而非冲突组。冲突组的定义是"差异大于价值"，只有不满足 complementary 的高摩擦才落入 conflicting。

**v6.3 变更说明**：

| 变更 | v6.2 | v6.3 | 理由 |
|------|------|------|------|
| 判定顺序 | homogeneous → conflicting → complementary | homogeneous → **complementary → conflicting** | 防止高互补被 conflicting 截胡 |
| complementary 条件 | `blindSpot − alignment ≥ 15` 且 avgDelta ∈ [0.25, 0.65] | `blindSpot ≥ 25` 且 `cogComp ≥ 70`（绝对阈值） | 解耦 alignment（v6.3 已删除）；绝对阈值替代相对 gap（相对 gap 在 random 下不可达） |
| conflicting 门槛 | frictionRisk ≥ 60 或两维 delta > 0.75 | frictionRisk ≥ **30** 或两维 delta > **0.50** | 随 dangerStart 校准同步降低 |
| complementary 检测率（50k） | 0.0% | **12.6%** | 判定修复生效 |
| conflicting 检测率（50k） | 0.0% | **0.3%** | 阈值校准生效 |

## 10. 适合一起挑战的任务（v6.2 重构）

> **产品定位**：不是能力匹配，是"你们的互补优势最能发挥的场景"。对外展示名："适合一起挑战的任务"，指标名："协同度"。  
> **设计原则**：fitScore 用互补分（dimScore）加权——描述协同潜力而非擅长领域。任务卡片的 reason/role/warning 全部动态生成（根据 strongestKey + 双方维度偏向）。

### 10.1 任务场景与权重

5 种赛博朋克世界观任务，仅 F/V/D 三核心维度参与拟合度计算（R 不参与，但作为协作提醒追加）：

| 任务 | 部门 | field | direction | vision | 解读 |
|------|------|:--:|:--:|:--:|------|
| 禁区探索 | 边界署 | .35 | .35 | .30 | 未知环境勘探，最看重判断参照 + 探索方向 |
| 应急响应 | 应急局 | .45 | .30 | .25 | 危机处理，最看重信息判断 |
| 标准审计 | 标准局 | .15 | .25 | .60 | 合规审查，最看重细节分析 |
| 黑市定制 | 黑市工坊 | .20 | .50 | .30 | 非标创新，最看重路径探索 |
| 遗迹发掘 | 遗迹司 | .15 | .35 | .50 | 数据解读，最看重信息结构 |

### 10.2 计算公式

```
fitScore = Σ (dimScore[key] × missionWeights[key])   // key ∈ {field, vision, direction}
strongestKey = argmax(dimScore[key] × missionWeights[key])
highPole = dimensionContexts[strongestKey].scoreA > scoreB ? callSignA : callSignB
```

取 top 3 展示。指标名"协同度"（代替"拟合度"）。

### 10.3 任务卡片文案（动态生成）

每张卡片 4 段：

| 字段 | 来源 | 示例 |
|------|------|------|
| 任务名 + 部门 + 协同度 | `missionWeights` + fitScore | `黑市定制 · 黑市工坊 · 协同度 82` |
| 适合原因 | `taskTemplate[任务名].reason(strongestLabel, strongestKey)` — 5 任务 × 3 维度 = 15 段专属文案 | `你们一个擅长打开可能性，一个擅长把想法收束成可执行的东西...` |
| 天然分工 | `dimensionRole[strongestKey](highPole, lowPole)` — 根据最强维度动态判定谁偏哪端 | `更偏定向的那方（星尘）负责筛选定稿，更偏探索的那方（零一）负责发散可能性` |
| ⚠ 协作提醒 | `taskTemplate[任务名].warning` — 仅 rhythm.pattern 为 friction/polarized 时追加 | `创意阶段别急着否定对方的想法——先把可能性全摊开...` |

**废弃项**：`missionReason`（3 pattern 模板）、`missionRoleSplit`（5 硬编码函数）→ 替换为 `taskTemplate` + `dimensionRole`。

| avg | 16.7 | 大部分用户盲区覆盖仍偏低，从用户感知角度，"认知互补 88 + 盲区覆盖 18" 会产生疑问："既然这么互补，为什么盲区覆盖才 18？" |
| p90 | 27 | 90% 用户 ≤ 27，与 cogComp p90=83 形成强烈视觉对比 |

**根因分析**：
- 同侧率 62.7% → coveragePotential 砍半
- 问卷 delta p50=0.19，整体区分度中等
- strengthFactor avg=0.3，大部分用户不在极端值

**后续观察方向**（待真实用户数据验证）：
- 目标：blindSpot avg 提升至 **20~25**
- 可能路径：① 问卷中增加"分化型"题目，拉大对侧组合比例（若 delta 问题）；② 调整 strengthFactor 权重使其更敏感（若 strength 问题）；③ 继续微调 coveragePower（若 power 仍有空间且不与其他指标共线）
- 判断标准：真实配对中 blindSpot p50 是否 ≥ 20（当前 random 模拟受限于随机对组合特性）

### 12.4 互补评分配置（`compatibility-report.config.js`）

维度参数、摩擦风险、聚合权重、评级映射、文案模块——详见第 9 节。

### 12.5 组合模式（Pair Pattern）判定规则

按优先级评估，**每对组合必定落在 4 个 pattern 之一**：

| 顺序 | 模式 | 条件 |
|------|------|------|
| 1 | `homogeneous` | 四维平均 delta < 0.15 |
| 2 | `conflicting` | `frictionRisk` ≥ 60 **且** `partnerIndex` < 75，**或** 两维及以上 delta > 0.75 |
| 3 | `complementary` | 盲区覆盖 ≥ 60 **且** 四维平均 delta ∈ [0.25, 0.65] |
| 4 | `asymmetric` | 兜底（不满足以上任一） |

设计原则：4 个维度（3 核心 + 1 风格标签）全部参与平均 delta 计算；盲区覆盖基于 3 核心维（见 9.3-B）；摩擦风险基于 4 维加权（见 9.3-C）；conflicting 增加总分上限防止高分误判；优先级从"最聚合"到"最分散"。已废弃的协作维度条件全部移除。

> 详细判定逻辑说明见第 9.6 节。

### 12.6 安全与健壮性

- **输入校验**：快照/题库版本两级校验；归一化分数 0-1 范围二次校验；friendId 正则校验防 KV key 注入；display 字段兜底
- **JSON 安全**：KV 读取使用 `safeParseJson()`；请求体 try-catch 包裹
- **错误信息策略**：生产错误由配置表提供，不泄露内部状态

### 12.7 版本升级流程

当升级题库或快照结构时：

1. 同时修改 `api-constants.js` 的 `API_VERSIONS` 和 `dualReport.ts` 的 `DUAL_REPORT_VERSIONS`
2. 同步更新前端 `buildResultSnapshot.ts` / `resultSnapshotService.ts`
3. 旧版本快照被 `validateSnapshotCompatibility()` 拦截返回 409，引导用户重新测评

## 13. 隐私与异常处理

### 13.1 标识与权限

- `friendId`：公开标识，用于分享和查询，可展示给用户
- `deleteToken`：私有凭证，仅本人本地保存，不展示、不拼进 URL、不分享
- `deleteTokenHash`：服务端仅存储 SHA-256 哈希

### 13.2 数据保留与最小化

- 结果快照默认保留 90 天，公开分享 7 天，到期自动删除
- 后端只保存生成报告所需的最小信息（归一化分数、主副原型、展示信息、版本时间戳）
- 不保存原始作答明细、本地 session 状态、非必要识别信息

### 13.3 异常场景速查

| 场景 | 处理 |
|------|------|
| 用户未保存自己的结果 | 提示"请先保存结果" |
| 识别码 不存在或已过期 | 返回 404 |
| 自己与自己比较 | 拦截并提示 |
| 版本不兼容 | 返回 409，提示重新保存 |
| 删除后旧识别码 仍可用 | 删除后立即失效，新报告请求返回 404 |
| 同设备多人轮流使用 | 前端提供"使用当前本地结果"或"重新测评"选项 |
