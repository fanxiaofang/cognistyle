## 2. 认知维度体系（三层架构）

### 2.1 第一层：核心认知维度（3 维 × 2 极）

认知风格的主体，决定用户的认知原型。

| 维度 ID | 维度名 | 左极 | 右极 | 说明 |
|---------|--------|------|------|------|
| `impulsive_reflective` | 认知节奏 | 冲动型 (Impulsive) | 反思型 (Reflective) | 行动驱动 vs 深度推演 |
| `convergent_divergent` | 信息策略 | 聚合型 (Convergent) | 发散型 (Divergent) | 规范收敛 vs 多维探索 |
| `wholistic_analytic` | 视野焦点 | 整体型 (Wholistic) | 分析型 (Analytic) | 宏观俯瞰 vs 局部细雕 |

| 维度 | 左极描述 | 右极描述 |
|------|---------|---------|
| 认知节奏 | 偏好快速迭代，通过动手写代码、建立快速原型和直接试验来理清思路 | 偏好在行动前做充足的调研分析，通过详细方案和推敲逻辑来寻找规律 |
| 信息策略 | 擅长自上而下的逻辑合拢，追求单一最优解和代码黄金准则 | 乐于探索各种边缘技术与非传统写法，思维开阔 |
| 视野焦点 | 目光聚焦于端到端业务闭环、系统骨架与商业价值 | 关注原子级细节、追求功能独立封装与极致的边界条件 |

### 2.2 第二层：协作偏好（1 维 × 2 极）

独立维度，不参与认知加工方式的判定，但影响最终身份合成。

| 维度 ID | 维度名 | 左极 | 右极 | 说明 |
|---------|--------|------|------|------|
| `solo_team` | 协作偏好 | 独行型 (Solo) | 协同型 (Team) | 独立沉浸 vs 团队共振 |

> 设计原则：协作偏好是"情境偏好"而非"人格特质"，仅用于 16 格身份合成中的 S/T 修饰。

### 2.3 第三层：知识表征（可选补充维度）

| 维度 ID | 维度名 | 左极 | 右极 | 说明 |
|---------|--------|------|------|------|
| `verbal_imagery` | 知识表征 | 言语型 (Verbal) | 表象型 (Imagery) | 文字逻辑 vs 视觉空间 |

> 该维度当前作为展示信息，参与计分但暂不参与原型匹配判定。双人报告主分只使用前 4 个维度。

## 4. 单人计分模型

### 4.1 Likert 量表

每题采用 5 点 Likert 量表：1=非常不同意 ~ 5=非常同意。未作答默认值=3（中立）。

### 4.2 单题计分

```
若题目方向 = 该维度右极：points = (userAns - 1) × 1.25
若题目方向 = 该维度左极：points = (5 - userAns) × 1.25
```

| userAns | 同向得分 | 反向得分 |
|---------|---------|---------|
| 1 | 0.00 | 5.00 |
| 2 | 1.25 | 3.75 |
| 3 | 2.50 | 2.50 |
| 4 | 3.75 | 1.25 |
| 5 | 5.00 | 0.00 |

### 4.3 维度聚合与归一化

```
dimRawScore = Σ(该维度所有题目的 points)
dimMaxScore = 该维度题目数 × 5
dimPercentage = (dimRawScore / dimMaxScore) × 100

normalizedScore = Math.round(percentage)        // 0-100 整数
polarity = percentage ≥ 50 ? 右极key : 左极key
strength:
  |normalized - 50| > 25 → "strong"
  |normalized - 50| > 10 → "moderate"
  else                   → "slight"
```

未设题目的维度默认 `percentage = 50`（中性）。

## 5. 原型匹配与身份合成

### 5.1 8 个认知原型（3 维笛卡尔积）

3 个核心认知维度各取两极之一，形成 2³=8 个原型：

| 原型 Key | 节奏 | 策略 | 焦点 | 行会 |
|----------|------|------|------|------|
| `I-C-W` | 冲动 | 聚合 | 整体 | 筑基者 |
| `I-C-A` | 冲动 | 聚合 | 分析 | 守门人 |
| `I-D-W` | 冲动 | 发散 | 整体 | 探路者 |
| `I-D-A` | 冲动 | 发散 | 分析 | 炼金师 |
| `R-C-W` | 反思 | 聚合 | 整体 | 筑基者 |
| `R-C-A` | 反思 | 聚合 | 分析 | 守门人 |
| `R-D-W` | 反思 | 发散 | 整体 | 探路者 |
| `R-D-A` | 反思 | 发散 | 分析 | 炼金师 |

### 5.2 欧氏距离匹配算法

将用户 3 维归一化得分映射到三维空间坐标（I=0, R=100; C=0, D=100; W=0, A=100），计算与 8 个理想原型顶点（如 I-C-W→[0,0,0], R-D-A→[100,100,100]）的欧氏距离：

$$D = \sqrt{(x_{target} - x_{user})^2 + (y_{target} - y_{user})^2 + (z_{target} - z_{user})^2}$$

最大可能距离 = √(100²×3) ≈ 173.2。匹配度折算：

$$\text{MatchScore} = \max\left(0, 100 - \frac{D}{173.2} \times 100\right)$$

### 5.3 主/副双形态决出

1. 对 8 个原型的 MatchScore 降序排列
2. **平局稳定排序**：分数相同时保留 `ARCHETYPE_KEYS` 数组原始顺序
3. 第 1 名=主形态（Primary），第 2 名=副形态（Secondary）

### 5.4 16 格身份合成

每个原型（8 个）× 协作模式（S 独行 / T 协同）= 16 格完整身份：

```
ProfileId = "{ArchetypeKey}-{ModeKey}"  例如: "I-C-W-S"
solo_team rawScore ≥ 12.5 → 'T'（协同），否则 → 'S'（独行）
```

16 格身份的详细档案（displayName / callSign / essence / cognitivePattern / workplaceEdge / collaboration / growthTip / visual 等）定义在 `src/data/suggestions.ts`。

### 5.5 四大行会与八大部门

## 7. 双人互补报告：功能设计

### 7.1 功能范围

- 用户完成单人测评后，保存结果快照并获得可分享的 `friendId`
- 输入好友 `friendId` 后生成双人认知互补度报告
- 双人报告通过分享链接进入
- 用户可主动删除自己的结果快照
- 生成脱敏公开分享报告

**不在范围**：不引入账号体系、不支持根据真实好友关系自动查找、不修改题库内容、不修改单人测评分数计算逻辑、不做多人团队版。

### 7.2 核心流程

**单人测评 → 保存快照**：用户完成测评 → 前端构建快照 → `POST /api/results` → 返回 `{friendId, deleteToken, expiresAt}` → 前端保存到 localStorage

**输入识别码 → 生成双人报告**：用户输入 `targetFriendId` → 读取本地 `myFriendId` → `POST /api/compatibility-report` → 返回 `CompatibilityReport` → 跳转双人报告页

**链接进入**：打开 `/dual?friend=<targetFriendId>` → 若本地有 `myFriendId` 则直接加载；若无则引导完成测评保存后再返回

**删除结果**：`POST /api/results/delete`（需 `friendId + deleteToken`）→ 后端校验 `deleteToken` → 删除快照 → 前端清理本地缓存

**公开分享**：`POST /api/share-report`（需 `myFriendId + targetFriendId`）→ 返回脱敏公开报告 token → 前端展示 `/share/<token>`

### 7.3 设计原则

- 保持现有单人测评与单人结果计算逻辑**完全不变**。
- 双人报告是**独立的业务模块**，不复用 `ResultsDisplay` 中的"第二身份"逻辑。
- `friendId` 只用于分享和检索；删除操作必须使用仅本人持有的 `deleteToken`。
- 互补度不是"越相反越高分"，而是**认知互补、协作兼容、盲区覆盖、摩擦风险**四个层面的综合判断。

### 7.4 数据模型

#### 结果快照 `ResultSnapshot`（服务端存储）

```typescript

  friendId: string;             // 服务端生成，公开标识
  deleteTokenHash: string;      // deleteToken 的 SHA-256 哈希
  category: 'general';

  snapshotVersion: string;      // 快照结构版本
  createdAt: number;
  expiresAt: number;

  profileId: string;            // 如 "I-C-W-S"
  primaryArchetype: { key: string; matchScore: number; };
  secondaryArchetype: { key: string; matchScore: number; };

  normalizedScores: {
    impulsiveReflective: number;   // 0=冲动, 1=反思
    convergentDivergent: number;   // 0=聚合, 1=发散
    wholisticAnalytic: number;     // 0=整体, 1=分析
    soloTeam: number;              // 0=独立, 1=协同
    verbalImagery?: number;        // 可选，不参与主分
  };

  display: {
    displayName: string;
    callSign: string;
    department: string;
    rank: string;
    avatar: string;
  };
}
```

#### 双人报告 `CompatibilityReport`

```typescript
interface CompatibilityReport {
  reportVersion: string;
  generatedAt: number;
  pair: { userA: {...}, userB: {...} };
  overall: { score: number; rating: string; summary: string; };
  breakdown: {
    cognitiveComplementarity: number;   // 核心认知互补度
    collaborationCompatibility: number; // 协作兼容度
```

## 8. API 设计

### 8.1 接口总览

| 接口 | 方法 | 说明 |
|------|------|------|
| `/api/results` | POST | 保存单人结果快照 |
| `/api/compatibility-report` | POST | 生成双人互补报告 |
| `/api/results/delete` | POST | 删除自己的结果快照 |
| `/api/share-report` | POST | 生成公开分享 token |
| `/api/share/:token` | GET | 获取公开分享报告 |

### 8.2 关键约束

- **双人报告使用 POST**：`myFriendId` 不适合暴露在 URL、日志和 CDN 缓存中。页面路由中保留 `targetFriendId`，接口层 `myFriendId` 放入请求体。
- **friendId 与 deleteToken 职责分离**：`friendId` 为公开标识（分享、查询），`deleteToken` 为私有删除凭证（仅本地保存一次，服务端只存 SHA-256 哈希）。
- **不允许仅凭 friendId 删除**：删除接口必须同时提交 `friendId + deleteToken`。

### 8.3 错误码规范

| 状态码 | code | 场景 |
|--------|------|------|
| 400 | `BAD_REQUEST` | 参数错误 |
| 404 | `NOT_FOUND` | 目标不存在或已过期 |
| 409 | `CONFLICT` | 版本不兼容 |
| 429 | `RATE_LIMITED` | 请求过频 |
| 500 | `INTERNAL_ERROR` | 服务异常 |

## 9. 互补计算模型

### 9.1 输入向量

从单人快照中提取 R（节奏）、S（策略）、V（视野）、C（协作）：

```text
delta = abs(scoreA - scoreB)
strengthA = abs(scoreA - 0.5) * 2
strengthB = abs(scoreB - 0.5) * 2
avgStrength = (strengthA + strengthB) / 2
oppositeSide = (scoreA - 0.5) * (scoreB - 0.5) < 0
```

### 9.2 维度互补评分函数（高斯核）

$$\text{dimScore} = \text{floor} + (100 - \text{floor}) \times \exp\left(-\frac{(\Delta - \text{idealGap})^2}{2 \times \text{tolerance}^2}\right)$$

当前实装参数（2026-05-30 校准）：

| 维度 | idealGap | tolerance | floor | 解释 |
|------|----------|-----------|-------|------|
| 节奏 `rhythm` | 0.28 | 0.22 | 8 | 峰值更靠近常见 delta；适度补位 |
| 策略 `strategy` | 0.38 | 0.25 | 3 | 中段差异最优 |
| 视野 `vision` | 0.35 | 0.27 | 5 | 中段差异，容忍度较高 |
| 协作 `collaboration` | 0.08 | 0.17 | 2 | 接近最好；极端的独立/协同冲突明显 |

### 9.3 四个子分

#### A. 核心认知互补度 `cognitiveComplementarity`

```
cognitiveComplementarity = rhythmScore × 0.30 + strategyScore × 0.35 + visionScore × 0.35
```

策略与视野是最容易形成实质互补的两条主维度，因此略高权重。

#### B. 协作兼容度 `collaborationCompatibility`

```
collaborationCompatibility = collaborationScore
```

只反映"合作方式是否顺手"，不代表是否互补，与核心认知维度不混算。

#### C. 盲区覆盖度 `blindSpotCoverage`

```text
coverageScore = 100 × gapFactor × sideBonus × strengthFactor

gapFactor     = max(0, 1 - |delta - 0.5| / 0.5)
sideBonus     = oppositeSide ? 1 : 0.6
strengthFactor = 0.4 + avgStrength × 0.6
```

取 3 个核心维度 coverageScore 的平均值。

#### D. 执行摩擦风险 `frictionRisk`

```text
riskScore = delta > dangerStart ? (delta - dangerStart) / (1 - dangerStart) × 100 × (0.5 + avgStrength × 0.5) : 0
```

| 维度 | dangerStart | weight |
|------|-------------|--------|
| rhythm | 0.40 | 0.40 |
| collaboration | 0.35 | 0.35 |
| strategy | 0.60 | 0.15 |
| vision | 0.65 | 0.10 |

```
frictionRisk = Σ(riskScore × weight)
```

### 9.4 总分公式

```
overallScore =
  cognitiveComplementarity × 0.50 +
  collaborationCompatibility × 0.15 +
  blindSpotCoverage × 0.25 +
  (100 - frictionRisk) × 0.10
```

homogeneous 模式额外施加 −5 分惩罚。

### 9.5 评级体系

| 分数区间 | 评级 | 解读 |
|----------|------|------|
| 80 - 100 | 王牌 | 互补明显且摩擦可控 |
| 65 - 79 | 合拍 | 有较强互补价值，需要少量协调 |
| 50 - 64 | 适配 | 部分维度互补，适合明确分工后合作 |
| 35 - 49 | 可期 | 有局部补位，但日常协作成本偏高 |
| 0 - 34 | 磨合 | 差异未形成有效协同，易互相消耗 |

homogeneous 模式（三围认知轮廓高度重合）评级固定为"认知重合"，不走常规 `getRating()`。

## 12. API 模块实现规范

### 12.1 模块结构

```
functions/api/
├── shared/
│   ├── api-constants.js      # 共享常量（版本号、Key 前缀、TTL、限流参数）
│   ├── api-utils.js          # 共享工具（限流/JSON/crypto/KV）
│   └── api-copy.js           # 共享文案（错误消息模板）
├── compatibility-report.js   # 互补报告生成（主逻辑）
├── compatibility-report.config.js  # 互补评分参数配置 + 文案
├── results.js                # 快照写入
├── results/delete.js         # 快照删除
├── share-report.js           # 公开分享创建

```

**依赖方向**：`shared/` 无循环依赖；`compatibility-report.config.js` 仅被 `compatibility-report.js` 引用；`share-report.js` 依赖 `compatibility-report.js`。

### 12.2 共享常量体系

#### 版本号

| 常量 | 值 | 与前端同步 |
|------|-----|-----------|
| `QUESTION_VERSION` | `questions-general-2026-06` | `src/contracts/dualReport.ts` → `DUAL_REPORT_VERSIONS` |
| `SNAPSHOT_VERSION` | `snapshot-v1` | 同上 |
| `COMPATIBILITY_REPORT_VERSION` | `compatibility-v1` | 同上 |
| `PUBLIC_SHARE_VERSION` | `public-share-v1` | 同上 |

#### KV Key 前缀

| 前缀 | 值 | 使用端点 |
|------|-----|---------|
| `RESULT` | `result:` | results / delete / compatibility-report |
| `SHARE` | `share:` | share-report / share/[token] |
| 限流前缀 | `rate-limit:xxx:` | 各端点独立 |

| 类型 | 有效期 |
|------|--------|

### 12.3 共享工具函数

| 函数 | 用途 |
|------|------|
| `hitRateLimit(kv, ip, prefix, max)` | 统一限流检查 |
| `json(body, headers, init)` | 统一 JSON 响应 |
| `getSnapshotKv(env)` | KV 绑定获取（四层兜底：`globalThis[已知名]` → `env[已知名]` → 扫描 `env` → 扫描 `globalThis`，兼容 EdgeOne/Cloudflare/本地） |
| `safeParseJson(raw)` | 安全 JSON 解析（返回 null 而非抛异常） |

| `generateUrlSafeToken(byteLength)` | crypto 安全随机 token（Base64URL） |
| `sha256Hex(input)` | SHA-256 hex 哈希，用于 deleteToken 校验 |

### 12.4 互补评分配置（`compatibility-report.config.js`）

维度参数、摩擦风险、聚合权重、评级映射、文案模块——详见第 9 节。

### 12.5 组合模式（Pair Pattern）判定规则

按优先级评估，**每对组合必定落在 4 个 pattern 之一**：

| 顺序 | 模式 | 条件 |
|------|------|------|
| 1 | `homogeneous` | 认知三维平均 delta < 0.15 **且** 协作 delta < 0.2 **且** 盲区覆盖 < 15 |
| 2 | `conflicting` | 摩擦 ≥ 60 **或** 节奏 delta > 0.75 **或** 协作 delta > 0.7 **或** 协作分 < 40 |
| 3 | `complementary` | 盲区覆盖 ≥ 60 **且** 平均 delta ∈ [0.25, 0.65] **且** 协作分 ≥ 60 |
| 4 | `asymmetric` | 兜底，不满足以上任一 |

设计原则：协作维度仅用于门槛判断，不参与认知维度平均 delta 计算；优先级从"最聚合"到"最分散"。

### 12.6 安全与健壮性

- **输入校验**：快照/题库版本两级校验；归一化分数 0-1 范围二次校验；friendId 正则校验防 KV key 注入；display 字段兜底
- **JSON 安全**：KV 读取使用 `safeParseJson()`；请求体 try-catch 包裹
- **错误信息策略**：生产错误由配置表提供，不泄露内部状态

### 12.7 版本升级流程

当升级题库或快照结构时：

1. 同时修改 `api-constants.js` 的 `API_VERSIONS` 和 `dualReport.ts` 的 `DUAL_REPORT_VERSIONS`
2. 同步更新前端 `buildResultSnapshot.ts` / `resultSnapshotService.ts`
3. 旧版本快照被 `validateSnapshotCompatibility()` 拦截返回 409，引导用户重新测评

## 13. 隐私与异常处理

### 13.1 标识与权限

- `friendId`：公开标识，用于分享和查询，可展示给用户
- `deleteToken`：私有凭证，仅本人本地保存，不展示、不拼进 URL、不分享
- `deleteTokenHash`：服务端仅存储 SHA-256 哈希

### 13.2 数据保留与最小化

- 结果快照默认保留 90 天，公开分享 7 天，到期自动删除
- 后端只保存生成报告所需的最小信息（归一化分数、主副原型、展示信息、版本时间戳）
- 不保存原始作答明细、本地 session 状态、非必要识别信息

### 13.3 异常场景速查

| 场景 | 处理 |
|------|------|
| 用户未保存自己的结果 | 提示"请先保存结果" |
| 识别码 不存在或已过期 | 返回 404 |
| 自己与自己比较 | 拦截并提示 |
| 版本不兼容 | 返回 409，提示重新保存 |
| 删除后旧识别码 仍可用 | 删除后立即失效，新报告请求返回 404 |
| 同设备多人轮流使用 | 前端提供"使用当前本地结果"或"重新测评"选项 |
